## 3. processed 字段映射

推荐器把处理后的字段映射到当前响应模型：

| processed 字段 | 推荐响应字段 | 用途 |
| --- | --- | --- |
| `business_id` | `business_id` | 商家唯一标识 |
| `name` | `name` | 商家名称 |
| `categories_normalized` | `categories` | 类别展示和关键词匹配 |
| `stars` | `rating` | 评分计算和结果展示 |
| `review_count` | `review_count` | 评论可信度分数 |
| `price_level` | `price_level` | 预算硬过滤和价格分数 |
| `latitude`、`longitude` | `distance_km` | 距离计算和半径硬过滤 |
| `attributes` | `reasons`、关键词文本 | 属性解释和关键词匹配 |
| `representative_reviews` | `evidence` | 推荐证据 |

代表评论按 `business_id` 分组后，只会附加到对应商家。每个推荐结果最多返回 2 条证据，`source` 使用处理后评论中的真实来源字段，例如 `yelp_review`。

## 4. 硬过滤规则

候选商家必须同时满足：

1. `is_open` 为真；
2. 城市与请求城市一致，默认城市为 Tampa；
3. `price_level` 存在且不高于请求预算；
4. 与请求坐标的球面距离不超过 `radius_km`。

对于 `price_level = null` 的商家，本阶段选择直接排除。原因是未知价格不能证明符合用户预算。

## 5. 评分规则

本段没有增加新模型，继续使用便于复现和解释的规则加权：

```text
关键词匹配       35%
商家星级         25%
评论量可信度     15%
距离             15%
价格             10%
```

关键词搜索范围包括商家名称、规范化类别、属性键和值、代表评论文本。排序仍按总分降序，并使用距离和 `business_id` 作为稳定排序条件。

## 6. API 变化

请求模型的默认城市由 Philadelphia 改为 Tampa。

推荐接口当前返回的引擎标识为：

```text
processed_geo_keyword_evidence
```

接口现在将全局 `ProcessedDatasetRepository` 传入推荐器，因此与数据状态接口共用 processed 数据目录和进程内缓存。

## 7. TDD 过程

| 轮次 | RED 失败原因 | GREEN 最小实现 |
| --- | --- | --- |
| 1 | 推荐函数不接受 processed 数据仓库参数 | 增加可选仓库参数并完成 Business、Review 字段映射 |
| 2 | `price_level = null` 执行 `int(None)` 报错 | 在价格比较前排除价格缺失候选 |
| 3 | processed `attributes` 是字典，旧 fixture 逻辑按列表切片并报错 | 统一把字典和列表属性转换为文本 |
| 4 | API 仍返回 fixture 引擎和 fixture 结果 | 默认城市切换为 Tampa，API 调用 processed 推荐路径 |

每轮均先运行定向测试观察预期失败，再加入最小实现并重新运行到通过。

## 9. 当前边界

- 当前仍是规则评分，不是训练出来的排序模型；
- 当前没有用户画像和个性化历史；

- 当前证据是代表评论直接映射，已经具备可追溯性，但不等同于完整 RAG；
- fixture 仅保留为兼容与回归测试入口。
