  核心知识点

  1. 双重检查锁（Double-Checked Locking）

  if _db_ready: return       # 第一次检查（快速路径，已初始化直接跳过）
  with _lock:                 # 加锁
      if _db_ready: return    # 第二次检查（防止多个线程同时等锁后重复初始化）
      # 建表 + 导数据...

  为什么需要两次检查？ 线程 A 和 B 同时发现 _db_ready = False，A 拿到锁开始初始化，B 阻塞等锁。A 释放锁后 B 如果不做第二次检查，就会再次建表。

  2. SQLite WAL 模式

  PRAGMA journal_mode=WAL（Write-Ahead Logging）：写操作写到一个单独的 WAL 文件，读操作继续读原始数据——写不阻塞读，读不阻塞写。对 Web 服务至关重要，否则同时有人查店铺和写日志会报
  database is locked。

  3. row_factory = sqlite3.Row

  不用这行代码，查询结果是 tuple，只能 row[0]、row[1] 这样按索引取，字段多了根本看不懂。用了之后 row["name"] 可以按字段名访问，和 dict 差不多，可读性大幅提升。

  4. utf-8-sig 编码

  Excel 导出的 CSV 文件头可能带 BOM（\ufeff），用普通 utf-8 读会把它当数据，导致第一行列名变成 \ufeffid 而不是 id。utf-8-sig 自动跳过 BOM。

  5. SQLite 连接不能跨线程共享

  这也是为什么每个函数都 _connect() 再 close()，而不是用一个全局 connection 单例。SQLite 同一个连接对象跨线程使用会出问题甚至崩溃。好在 SQLite 本身很轻量，打开连接几乎零开销。

  ---
  核心知识点

  1. 关键词匹配 vs LLM — 为什么先做规则不做 AI

  校园餐饮场景的词汇非常集中（就那么几种口味、几个校区、几个时间段），关键词表覆盖 90% 的情况。它的优势是：
  - 毫秒级，不走网络
  - 零成本，不烧 API 额度
  - 结果稳定可解释，同一输入永远同一输出

  LLM 是增强不是替代——后面章节会用它来做 rerank（重排序），但在规则已经能搞定基础匹配的情况下没必要把每个请求都丢给大模型。

  2. 二元匹配 vs 梯度打分

  当前每个维度匹配就是满分，不匹配就是 0，不做梯度。原因是数据量小（几十家店），标签只记录了"有没有"（例如 tastes 字段是 ["麻辣",
  "重口"]），没有强度、程度这类连续值。数据粒度决定了打分粒度——标签没有梯度，打分硬造梯度反而不准。

  唯一的例外是预算维度做了梯度打分：budget_score = max(0, 1.0 - (budget_max - price) / budget_max)，价格越接近预算上限分越低。因为价格本身是连续值，天然可以做梯度。

  3. 权重为什么要"过度叠加"而不是归一化

  五维权重 + base_score + budget_bonus 是并行叠加的，加起来远超 1.0，最终靠 min(total, 0.99) 裁剪。这个设计的逻辑是：
  - 如果归一化（每个维度满分只有 1/N），多维度匹配和少维度匹配的分数差距太小，排不出优劣
  - 叠加之后每条规则独立贡献，匹配越多分越高，区分度更大
  - 上限裁剪是安全网，防止某个店铺因为全匹配而溢出

  4. 营业时间的重叠判断

  _is_open_during() 用的是区间重叠算法：把时段起止时间和店铺营业时间都转成"从零点开始的分钟数"，然后判断 shop_open <= slot_close AND shop_close >=
  slot_open。用分钟数而不是小时数做比较是避免浮点边界问题的经典做法。

  5. 场景别名（alias）的设计意义

  用户不会说"我要同学聚餐场景的餐厅"，而是说"跟室友出去吃"、"和朋友约饭"、"宿舍聚餐"。scene_aliases 把各种口语化说法映射到 3
  个标准场景（一个人/同学聚餐/约会），解析器提取标准槽位，推荐引擎再用别名展开匹配。这是搜索系统和推荐系统常用的同义词归一化思路。



   这四个文件按依赖关系从上到下构成了一条流水线：

  scoring_config.yaml          ← 你可以手动调的"旋钮"
          ↓
  scoring_config.py            ← 把旋钮读进程序，旋钮坏了用默认值兜底
          ↓
  parser.py                    ← 把用户大白话拆成 5 个筛选条件
          ↓
  recommender.py               ← 用筛选条件给每家店打分 → 排名 → 返回

  ---
  1. scoring_config.yaml — 权重配置文件

  这是你可以手动调参的文件，不用改代码。三块内容：

  weights（权重）：决定推荐时每个因素的"话语权"。scene（0.22）和
  budget（0.22）权重最高，意思是"跟谁吃"和"花多少钱"比"吃什么口味"更重要。

  time_slot_ranges（时段定义）：把一天分成四个时段。26:00 代表次日凌晨 2
  点——因为夜宵可能跨过午夜，用 26 小时制避免时间比较出错。

  scene_aliases（场景别名）：用户在文本框里不会说"同学聚餐"，而是说"跟室友出去"、"约饭"
  、"聚会"。这张表把口语→标准场景做了映射。

  ---
  2. scoring_config.py — 配置加载器

  核心就一个函数 load_scoring_config()，做了三件事：

  1. 读 YAML 文件（也支持 JSON，看后缀名）
  2. 深度合并 _deep_merge()：把 YAML 里的值覆盖到硬编码的 _DEFAULT_CONFIG
  上。比如你只改了 weights.budget，那其他所有字段（time_slot_ranges、scene_aliases
  等）不受影响，保持默认值
  3. 兜底：配置文件删了、写错了、格式坏了——直接返回 _DEFAULT_CONFIG，程序不崩

  还有一个环境变量 SCORING_CONFIG_PATH，允许你在服务器上指定不同的配置文件路径。

  ---
  3. parser.py — 查询解析器

  把"清水河，预算25，一个人想吃清淡的"这种大白话变成 5 个结构化字段。

  ParsedSlots：一个 dataclass，就 5 个可选字段：
  budget_max: float | None   # 预算上限，比如 25.0
  location: str | None       # "清水河" 或 "沙河"
  scene: str | None          # "一个人" / "同学聚餐" / "约会"
  taste: str | None          # "清淡" / "麻辣" / "鲜美"
  time: str | None           # "早餐" / "午餐" / "晚餐" / "夜宵"

  提取方式：
  - 预算用正则 (\d{1,3})\s*(元|块)?\s*(以内|以下|左右|预算)? —— 匹配
  "25元"、"30以内"、"预算50" 等，超过 500 视为无效（可能是乱输入的）
  - 其他四维用 _match_any() 函数，在 4 张关键词表里遍历匹配，找到第一个就返回

  设计考虑：关键词表顺序决定优先级。比如 _SCENES 里"一个人"排在"同学聚餐"前面，因为"一
  个人"的关键词里包含"简单"、"随便"，如果不优先匹配会误判。

  ---
  4. recommender.py — 推荐排序引擎

  整个项目最核心的算法文件。对外只暴露一个 recommend(parsed, top_k)。

  流程：

  1. 从 SQLite 取全部 8 家店铺
  2. _score_shop() 逐家打分：
    - 基础分 0.15（每家都有）
    - 预算匹配：梯度打分，1.0 - (预算上限 - 价格) / 预算上限。25 块预算，12 块的店比 22
   块的店分高
    - 校区匹配：campus_text = "清水河 西门"，检查 "清水河" 是否在字符串中
    - 口味匹配：把 tastes JSON 字段（如 ["麻辣", "重口"]）解析成列表，做精确匹配
    - 场景匹配：先通过 scene_aliases 把槽位展开成同义词列表，再做模糊匹配
    - 时间匹配：_is_open_during() 用区间重叠算法判断营业时间与时段是否有交集
    - 预算附加分：0.03，仅限预算匹配的店
  3. 最终分数 min(total, 0.99) 裁剪
  4. _build_reason() 生成中文推荐理由，如
  "预算匹配，校区匹配，口味匹配，场景匹配（综合评分 0.95）"
  5. 排序：分数降序 → 价格升序（同分时便宜优先）→ ID 升序
  6. 截断返回 top K

  过滤逻辑：if matched or parsed.budget_max is None ——
  至少匹配一项才返回；如果用户只设了预算（没匹配到任何维度），也不返回（因为只有预算不
  够，需要至少一个偏好维度）。但如果用户什么都没设（空 query），全量返回。

  核心知识点

  1. APIRouter — 路由分组

  用 APIRouter() 把相关端点打包成一个模块，然后通过 app.include_router(router, prefix="/api/v1") 挂载。这样做的好处是：
  - main.py 保持干净，不随着端点增多而膨胀
  - 不同版本的 API（v1、v2）可以放在不同 router 里独立管理
  - 端点的路径前缀集中控制（/api/v1），不用在每个函数上写

  2. Pydantic 的自动校验

  RecommendRequest 里 query: str = Field(..., min_length=1) 中的 ... 表示必填，min_length=1 表示不能是空字符串。如果有人请求 {"query": ""}，FastAPI 在进入你的函数之前就返回 422
  Unprocessable Entity，你的代码永远不会拿到脏数据。这是 Pydantic 最大的价值——在边界处拦截非法输入，内部代码可以信任数据一定合法。

  3. response_model 的双重作用

  给路由装饰器加 response_model=RecommendResponse 有两个作用：
  - 文档生成：Swagger 自动显示返回值的字段结构
  - 输出过滤：函数返回的 dict 里多余的字段会被自动删除，只保留模型定义的字段。这意味着你的内部数据结构可以比对外暴露的更丰富，不会意外泄露

  4. HTTPException 的用法

  raise HTTPException(status_code=404, detail="店铺不存在")

  这是 FastAPI 推荐的处理异常方式——不要手动构造 {"error": "..."} dict 返回，而是 throw 一个 HTTPException，FastAPI 会自动转换成标准 JSON 错误响应。这比在控制器里到处 if-else +
  return 干净得多，错误处理逻辑不淹没业务逻辑。

  5. 为什么热门排行用 GET 而推荐用 POST

  - GET /rankings/today — 排行是无状态查询，不需要请求体
  - POST /recommend — 推荐请求带有 query + top_k 参数，语义上是在"提交一次推荐请求"，而且未来可能扩展更多参数（filter、context 等），POST body 更灵活

  用 GET 还是 POST 的判断标准不是"有没有参数"，而是操作是否有副作用和参数的复杂度。推荐虽然是"读"操作，但参数是结构化的，用 POST body 传比塞在一长串 query string 里更合适。

  1. JWT 三段式结构：base64(Header).base64(Payload).HMAC-SHA256签名，手写 70 行可完整理解原理
  2. hmac.compare_digest()：恒定时间比较签名，防时序攻击
  3. Base64 URL Safe：去掉 =、替换 +/ 为 -_，URL 中不用转义
  4. FastAPI 依赖注入鉴权：Depends(require_authenticated_user) + Header(None) 自动注入 Authorization
  5. openid 哈希保护：sha256(salt:openid)[:24] 单向不可逆，拖库也不泄露原始 openid
  6. OAuth code2session：wx.login() → code → 微信服务器 → openid → 自己的 JWT
  7. 匿名优先身份体系：先分配匿名 ID，登录后通过 /profile/sync-local 合并历史数据

  知识点

  - Next.js App Router："use client" 标记客户端组件，layout.tsx 是根布局，page.tsx 是首页路由
  - 匿名优先身份体系：前端生成匿名 ID（不依赖后端），登录后通过 upgradeIdentity() 静默升级，token 过期自动降级
  - Blob UTF-8 编码：new TextEncoder().encode(json) → new Blob([bytes], {type: "application/json"})，比直接传 JSON 字符串更可靠地保留中文
  - 防抖（debounce）：用户输入后等 250ms 无新输入才发 API 请求，减少无效网络调用
  - CSS 玻璃态：backdrop-filter: blur(12px) + 半透明背景 + 细边框 = 毛玻璃卡片效果
  - Shimmer 骨架屏：linear-gradient + animation 模拟内容加载中的占位效果，比转圈更友好
  - 两阶段 URL 解析：NEXT_PUBLIC_API_BASE_URL → localhost 检测 → 生产 Render URL，无需改代码切换环境
